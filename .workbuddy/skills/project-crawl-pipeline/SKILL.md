# 本项目的抓取功能

## ★ 动手前先跑自检

```bash
python 05_技能/selfcheck.py            # 全量
python 05_技能/selfcheck.py --quiet    # 只看「错误」和「警告」
```

八项检查：**密钥 / 落盘命名 / 逐字稿截断 / 封面覆盖 / 条数对账 / 四层结构 / 配置残留 / 表里「未知」**。

**这份脚本是下面那些检查条目的替代品。** 能脚本化的（命名合规、长度是否撞顶、封面覆盖率、
产出与源数据是否对得上、密钥有没有混进进 git 的文件）已经写进它了 ——
脚本跑一次给确定的答案，比让 AI 记住几十条清单可靠。

**人脑该记的是判断标准**（下面「判断标准速查」那节），不是可执行的检查。

## 项目里有哪几条抓取线

| 源 | 在哪儿 | 能抓什么 | 花钱 |
|---|---|---|---|
| **灵造** | `01_采集/01_lingzao/` | 博主主页全量（`profile`）、关键词搜笔记（`search`） | **是**。`profile` 按条数 **50**（1–20 条）/ **100**（21–40 条），`search` 20/次。价目以官方 `playbooks/search-credit-notice.md` 为准。**动它之前必须先报账** |
| **得到大脑** | `01_采集/02_getnote/` | **外抓**：订阅博主的逐字稿、封面、指定链接转结构化笔记 | 否（会员制，只占次数） |

**一个源一个文件夹，各自完全自包含**：`config.json` + `collect.py` + `README.md`，
拷到别处也能独立跑。卸载一个源 = 删掉那个文件夹。
代价：两份 `collect.py` 的工具代码重复，改 bug 要改两遍（**用户已拍板接受这个代价**）。

```
01_采集  →  02_储存  →  03_加工  →  04_产出
抓回来      原始数据     清洗转换     能用的东西

05_技能                                    ← 规范 / 复盘 / 手册
                                             （上面四层怎么搭、怎么改）
```

## 铁律：三层各管各的，不许串

| 层 | 只放什么 | 不许出现 |
|---|---|---|
| `02_储存` | 采集回来的**原始东西，原封不动** | 逐字稿、封面、任何加工品 |
| `04_产出` | 洗过的表、逐字稿、封面、索引 | — |

判断标准：**没经过代码加工的东西进 02，加工过的进 04。** 逐字稿和封面都是产出。

## 标准流程

```bash
# 1. 采集 —— 两个源都「一条命令走到底」：抓完自动接清洗，04_产出 里直接有东西
#
#   灵造（付费源，不加 --go 只预演、不花钱）
python 01_采集/01_lingzao/collect.py profile --url "<小红书主页URL>" --limit 40 --go
#     落盘后顺带：抢封面（链接 3 小时过期）+ 下完整字幕合集（免费）
#
#   得到大脑（会员制，全走 HTTP API，不花积分、不用 --go）
python 01_采集/02_getnote/collect.py bloggers --topic <topic_id>
python 01_采集/02_getnote/collect.py details  --topic <topic_id> --follow <follow_id> --limit 20
#
#   --no-clean 关掉自动清洗，只抓不出表。加工层被删了也不影响采集。

# 2. 加工（每源一个入口；正常不用手跑，上面已自动接上）
python 03_加工/01_lingzao/run.py  <search|table|bundle|cover|video> "<路径>"
python 03_加工/02_getnote/run.py <blogger|table|cover|video>        "<路径>"
#    灵造 bundle 既吃 profile JSON，也吃历史成品表 xlsx
```

### ★ 抓完必须接加工 —— 别把「抓完了」当成任务完成

采集只是把数据落进 `02_储存`。**不跑加工，`04_产出` 里就什么都没有，用户根本看不见。**

这是用户最在意的一条，原话：

> 「你抓到数据之后**不会主动调用文件做清洗**」
> 「只会抓到这些文件里，但是没有到产出成的话，**我是看不清也看不见的**，就有一点一言难尽」

**2026-09-20 起两个 `collect.py` 都自动接上了**（真抓成功后自己调对应的 `run.py`，
`--no-clean` 可关）。手动重跑时用：

| 抓了什么 | 紧接着跑什么 |
|---|---|
| 灵造 `profile` | `03_加工/01_lingzao/run.py bundle "<路径>"` |
| 灵造 `search` | `03_加工/01_lingzao/run.py search <路径>` |
| 得到大脑 `details` | `03_加工/02_getnote/run.py blogger "02_储存/02_getnote/blogger"` |

**判据：没在 `04_产出` 里看见东西，就等于这次没干活。**

### 产出结构与命名规矩

```
04_产出/博主/<昵称>_<账号ID>/
    _索引.xlsx              统一字段 30 列，见 03_加工/columns.md
    _逐字稿合集.md           只有灵造有（得到大脑没有「合集」这个概念）
    <发布日期>_<标题>/
        逐字稿.md            信息头 + 正文 + 逐字稿（一个文件看全貌）
        封面.webp / .jpg      有才放
04_产出/图片/<昵称>_<账号ID>/<笔记ID>.webp    封面池（缓存）
04_产出/表格/                                  成品表
```

- 博主目录 = `昵称_账号ID` —— 改昵称了也能对回账号
- 单条目录 = `发布日期_标题`，**不用 `001` 序号** —— 增量抓时序号会错位
- 单条目录里的文件名**固定**（`逐字稿.md` / `封面.\*`）—— 固定了才能一个脚本跑全部博主
- 身份永远认**唯一 ID**（笔记 ID / `post_id_alias`），文件夹名只是给人看的
- 标题清洗只清半角 `\/:*?"<>|`（全角 `？！：` 合法，别误伤）+ 40 字截断

## 下载：封面 / 视频

**三条规则（用户拍板，别改）：下载归加工层；按源分开；封面和视频各自成文件。**
用户原话：「因为每一个就是他们的脚本规则是不一样的，有的抓的是**临时链接**，有的是抓的是**永久链接**。」

| 文件 | 干什么 | 要凭证吗 |
|---|---|---|
| `03_加工/01_lingzao/cover.py` | 读本地 profile JSON（也吃成品表 xlsx）→ 下到图池 | 不要 |
| `03_加工/02_getnote/cover.py` | 读本地详情 JSON → 下到图池 | 不要 |
| `03_加工/<源>/video.py` | 视频**占位接口**，不下载任何东西 | — |

**两个源的封面脾气完全不同 —— 这就是要分开写的原因：**

| | 灵造 | 得到大脑 |
|---|---|---|
| 签名 | **带**（`t=` 时间戳） | **不带** |
| 有效期 | **约 3 小时**，过了全 498 | **永久** |
| 语义 | **抢救**（晚了就废） | **补缺**（什么时候都行） |
| 字段 | `media.cover_large_url` | `post_cover` |

⚠️ **别把一边的紧张感套到另一边。** 灵造窗口一过就真没了（JSON 里存的是**已经签好名**的
URL，过期即废纸，想拿新的只能重抓 = 花 credits）；得到大脑随时可补。

**得到大脑的封面不用单独补**：详情接口就带 `post_cover`，采集时随 JSON 一起落盘，
表里第 29 列「封面URL」直接有值。封面**图**由 `bundle.py` 归位 ——
**先取图池，图池没有就用手上那个 URL 现下**，所以封面不会缺。

**视频为什么是空的**：灵造只给**时长**不给地址（而且两种命令字段名不一样：
`media.video_duration_seconds` / `media.video.durationMs`）；得到大脑的 `post_url`
是抖音**分享页**，不是 `.mp4` 直链。要真下得再加解析层 = 新增依赖。
所以先摆「接口 + 询问流程」：**抓完先问用户 —— 有几条视频、要不要下、多少钱、占多大**。
默认「下」，也可以改成不下，但**不管默认是什么都先问一次**（要报成本，不能闷头下）。

## 得到大脑（getnote）的外抓链路

**⚠️ 大前提：只用「外抓」命令，不碰用户私人笔记**（2026-09-19 用户划的边界）。

### 一律走 HTTP API，不用 CLI（2026-09-20 用户定）

理由：HTTP 详情给 **12 个字段、带 `post_cover`（封面）**；CLI 只有 10 个、没有封面。
走一条通道，就少一处「两边不一致」。

```bash
python 01_采集/02_getnote/collect.py bloggers --topic <topic_id>             # 博主列表 → follow_id
python 01_采集/02_getnote/collect.py contents --topic <topic_id> --follow X   # 内容列表 → alias 清单
python 01_采集/02_getnote/collect.py details  --topic <topic_id> --follow X   # ★ 详情 → 跑完自动出表
```

```
GET /bloggers?topic_id=                              博主列表
GET /blogger/contents?topic_id=&follow_id=&page=     内容列表
GET /blogger/content/detail?topic_id=&post_id=       内容详情 ★ 逐字稿 + 封面
   头：Authorization: <api_key>（⚠️ 不带 Bearer） + X-Client-ID: <client_id>
```

`--limit` 默认 20；`--gap` 默认 3.5 秒（被限流就调大）；`--no-clean` 关掉自动清洗。

### 禁用（碰私人笔记，一条都不许调）

`notes` / `note` / `note original` / `note transcript` / `note attachments` /
`note timeline` / `note quick-note` / `note todos` / `search` / `tag *` /
`kb`（知识库笔记列表）/ `save` / `note update` / `note delete` / `note share`

⚠️ 这是**约定隔离**，不是权限隔离 —— CLI 用的是用户账号的完整授权，
脚本不调 ≠ 权限上读不到。唯一例外：**用户当轮明确点名**要看自己某条笔记时可以调，
但那不是常规动作，也不许写进 `ACTIONS`。

### 落盘命名（改名字之前，先去加工层确认它靠什么认文件）

```
02_储存/02_getnote/blogger/
    _bloggers_<昵称>_<follow_id>.json          博主列表
    _blogger-contents_<昵称>_p1.json           内容列表
    _blogger-content_<post_id_alias>.json      单条详情
```

两条硬要求：**不能带日期前缀**（跨天并存 → 同一条变两个文件 → 加工层读双份）；
**必须保住前导 `_`**（加工层靠 `*_blogger-content_*` 这种 glob 认文件）。

### 指定链接 → 结构化笔记（`save`）

```bash
"$EXE" save "<链接>" --title "<原帖标题>" --idempotency-key <key> -o json
```

- **同步的**：约 40 秒直接返回完整笔记，**没有 task_id、不用轮询**。
  官方文档说普通链接是异步（要轮询 `task/progress`）—— 那是 **HTTP API** 的行为，
  **CLI 把异步包装成了同步**。别白写一套轮询逻辑。
- **一次调用全给你**：`data.note` 里同时含 `content`（AI 解读版）和
  `web_page.content`（原文版），不需要再调 `note`。
- 它接受**任意网页链接**，不限小红书 —— 这才是它比灵造值钱的地方。
- 实测 `source: openapi`（手动在 App 里存的是 `app`），能区分两种来源。

## 判断标准速查 ★ 全是实测踩出来的

> 可执行的检查已移进 `05_技能/selfcheck.py`。**这一节只留判断标准** ——
> 也就是「看到什么现象，说明什么问题」。

### ① 灵造的封面过了窗口就真没了

`t=` 是**抓取那一刻**的十六进制时间戳，签名约 3 小时。实测：16:11 抓的 19:23 去下 → 全废；
8-04 的 40 条 → 24 条 498 + 16 条 403，**一张都没救回来**。
所以**采集时当场抢是主路**，`run.py cover` 只是窗口内补救。

### ② 逐字稿有「三态」+「截断」两层，别混为一谈

**缺稿分三种**，先看**字幕状态**和**时长**：

| 情况 | 特征 | 重抓有用？ |
|---|---|---|
| `failed` | 有时长、媒体信息齐全 | ✅ **实测 18 条修好 17 条** |
| `missing` + 有时长 | 时长 11s/18s 这种 | ❌ 白花钱（视频本身没人声）|
| `missing` + 时长为 `None` | 媒体信息整个拿不到 | ❓ 未知 |

**别把「没抓到」和「源头没有」混为一谈。**

**再看截断**：JSON 里 `subtitle.plain_text` 是**截断版**（实测卡 1203 字，
16 条里 14 条正好撞顶）。全文在**响应顶层** `data.artifacts.subtitle_markdown.url` ——
**不在 `items[].artifacts`**（那个是空的，查错地方会误判成「没有全文」）。
采集层已自动下成 `<源JSON名>_完整字幕合集.md`，旁边还有 `<源JSON名>_artifacts.json`
记着 URL / `sha256` / 下载结果 —— **想重下全文查那份小文件**。

📏 **判断依据：各条长度一样 = 截断；长度各异 = 全文。**（脚本会直接报）

### ③ 逐字稿必须按**唯一 ID** 匹配，绝不能按标题

**同一个博主会有同名笔记**。实测 nana 账号里有两条都叫「Codex 一键智能剪辑 Skill 开源了！」
（08-08 和 08-12）。按标题匹配必然串行。合集里每条都有 `- 笔记 ID:`，用它对齐。

### ④ ★ 标题一个字都不许改（用户定的铁律）

得到大脑 `save` 会用 AI **重写标题**。实测原帖「恐惧很深的人，乐在其中，会很有厚度」
→ 存进去变成「深度认知：恐惧深厚个体的人生成长路径解析」。

**原标题去哪找：`attachments[0].title`（三条全验证过）**

- ⛔ **别按长短判断它是不是标题** —— 小红书的标题**常常就是正文第一句**，按「长的就是正文」判会误判
- 可能被服务端截断；`source` 无论 `app` / `openapi` / `web` 这个字段都有值

⚠️ **分享文本的坑**：`【<标题> - <作者> | 小红书…】` 里的 **` - <作者>` 不是标题**。
→ **最佳做法：`save` 完回读一次，用 `attachments[0].title` 校正**（服务端才是权威）。
→ `save` **必须带 `--title`**；用户粘的常是**整段分享文本**，动作要能同时抠出标题和 URL。
→ 已存错要改回来：`getnote note update <id> --title "..."`（**改 title 不需要 `--yes`**，改完必须重读验证）。

### ⑤ 改落盘命名前，先看加工层靠什么认文件

项目里认文件名的地方有**两处**：**glob**（`bundle.py` 的 `*_blogger-content_*`）×
**正则**（`adapter.py` 的 `_RE_*`）。改名要同时过这两关，否则文件明明在那儿、
加工层却说「没有」。

**★ 派生文件（合集、缩略图、附属数据）必须用主文件「实际落盘后」的名字配对** ——
`save_raw()` 遇重名会加 `_2`，用你「打算」写的名字会配不上。

### ⑥ 测试「某个东西不可用」时，屏蔽手段要真的破坏匹配条件

想验证「图池不可用时会不会现下兜底」，把目录改名成 `__Bak_谢胜子_1397022` ——
**它仍然以 `_1397022` 结尾**，而匹配规则正是「目录名后缀 = 账号ID」，照样命中，
测出来的是假象。**先确认你的屏蔽真的能让它不被找到**，且用 `try/finally` 恢复现场。

### ⑦ 链接笔记有两个正文，是两个不同的字段

- `web_page.content`（= `note original` 的 `original`）= **网页原文**
- `content` = **得到大脑 AI 二次加工的结构化笔记**（带表格和洞察，`entry_type=ai`）

**一份内容两条正文，入库前要想清用哪条**，别默认只取一个。（**这一条还没定，等用户拍板**。）

### ⑧ 得到大脑有桶级限流

`429 / code 10202 / reason=qps_bucket_exceeded / retryable: true`。
**连着调两个接口就撞上，等 4 秒恢复** → 每条之间停 **3.5 秒**起。
实测 20 条详情 105 秒 → 665 条约 58 分钟。额度（read）日 20000 / 月 200000 够用，
**撞的一定是 QPS 桶，不是配额**。

### ⑨ 文档的字段表不可信，实测往往更多

得到大脑详情接口官方只写 6 个字段，**实测 12 个**；博主内容列表官方写 5 个，实测 12 个。
**别拿文档的字段表当白名单校验**，会漏数据。写适配器前先把真实响应 dump 出来看。
（灵造那边也出现过文档枚举里没有的 `class_audio`。）
