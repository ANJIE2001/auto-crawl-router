# 本项目的抓取功能

## 接到任务先读什么

| 你接到什么 | 先读 |
|---|---|
| **要加一个新渠道（第 3 个源）** | `05_技能/新增渠道规范.md` —— 骨架、采集层六个必须有、加工层八个文件职责、验收清单 |
| 某个东西行为怪、数据对不上 | 本文档下面「纠错清单」那节，按现象查 |
| 想推翻某个设计 | `05_技能/开发复盘.md` —— 当初为什么这么定 |
| 查灵造的参数 / 积分 / 脚本路径 | `05_技能/灵造使用说明.md`（官方手册快照）|

**加新源是这套结构唯一的扩展方式**，规范已经固化，别临时发挥。

## 项目里有哪几条抓取线

| 源 | 在哪儿 | 能抓什么 | 花钱 | 现状 |
|---|---|---|---|---|
| **灵造** | `01_采集/01_lingzao/` | 博主主页全量（`profile`）、关键词搜笔记（`search`） | 是。价目以官方 `playbooks/search-credit-notice.md` 为准（`profile` 按 1–20 条 **50** / 21–40 条 **100** 分档，`search` 20/次）。**动它之前必须先报账** | 主干，采集→加工→产出端到端打通 |
| **得到大脑** | `01_采集/02_getnote/` | **外抓**：订阅博主的逐字稿、封面、指定链接转结构化笔记。⚠️ 碰私人笔记的命令本项目**禁用** | 否（会员制） | 博主链路 + 封面 + 链接链路已实测跑通；**链接笔记的适配器待写** |

**一个源一个文件夹，各自完全自包含**：`config.json` + `collect.py` + `README.md`，
拷到别处也能独立跑。卸载一个源 = 删掉那个文件夹。
代价：两份 `collect.py` 的工具代码是重复的，改 bug 要改两遍（已确认接受这个代价）。

```
01_采集  →  02_储存  →  03_加工  →  04_产出
抓回来      原始数据     清洗转换     能用的东西

05_技能                                    ← 规范 / 复盘 / 手册
                                             （上面四层怎么搭、怎么改）
```

## 铁律：三层各管各的，不许串

| 层 | 只放什么 | 不许出现 |
|---|---|---|
| `02_储存` | 采集回来的**原始东西，原封不动** | 逐字稿、封面、任何加工品 |
| `04_产出` | 洗过的表、逐字稿、封面、索引 | — |

判断标准：**没经过代码加工的东西进 02，加工过的进 04。** 逐字稿和封面都是产出。

## 标准流程

```bash
# 1. 采集 —— 两个源都「一条命令走到底」：抓完自动接清洗、04_产出 里直接有东西
#
#   灵造（付费源，不加 --go 只预演、不花钱）
python 01_采集/01_lingzao/collect.py profile --url "<小红书主页URL>" --limit 40 --go
#     落盘后顺带：抢封面（URL 3 小时过期，见纠错 ②）+ 下完整字幕合集（免费，见纠错 ⑤）
#
#   得到大脑（会员制，**全走 HTTP API**，不花积分、不用 --go）
python 01_采集/02_getnote/collect.py bloggers --topic <topic_id>
python 01_采集/02_getnote/collect.py details  --topic <topic_id> --follow <follow_id> --limit 20
#
#   --no-clean 关掉自动清洗，只抓不出表。加工层被删了也不影响采集。

# 2. 加工（每源一个入口；正常不用手跑，上面已自动接上）
python 03_加工/01_lingzao/run.py  <search|table|bundle|cover|video> "<路径>"
python 03_加工/02_getnote/run.py <blogger|table|cover|video>        "<路径>"
#    灵造 bundle 既吃 profile JSON，也吃历史成品表 xlsx

# 3. 下载（封面 / 视频各自一个文件，两个源各写各的 —— 规则不一样，见下一节）
python 03_加工/01_lingzao/run.py  cover "<路径>"   # 灵造：带签名链接，越早跑越好
python 03_加工/02_getnote/run.py cover "<路径>"   # 得到大脑：永久链接，随时补
python 03_加工/01_lingzao/run.py  video "<路径>"   # 占位，不下载任何东西
```

**★ 抓完必须接加工 —— 别把「抓完了」当成任务完成。**

采集只是把数据落进 `02_储存`。**不跑加工，`04_产出` 里就什么都没有，用户根本看不见。**
这个是用户最在意的一条，原话：

> 「你抓到数据之后**不会主动调用文件做清洗**」
> 「只会抓到这些文件里，但是没有到产出成的话，**我是看不清也看不见的**，就有一点一言难尽」

所以每次采集成功后，**在同一个回合内**把对应的加工跑掉，别留给「下一步」：

| 抓了什么 | 紧接着跑什么 |
|---|---|
| 灵造 `profile` | `03_加工/01_lingzao/run.py bundle "<路径>"` |
| 灵造 `search` | `03_加工/01_lingzao/run.py search <路径>` |
| 得到大脑 `details` | `03_加工/02_getnote/run.py blogger "02_储存/02_getnote/blogger"` |

★ **2026-09-20 起这几步都自动接上了**：两个 `collect.py` 真抓成功后自己就调对应的
`run.py`（`--no-clean` 可关）。上表是**手动重跑**时用的，不是每次都要求你做。

**判据：没在 `04_产出` 里看见东西，就等于这次没干活。**

产出结构（博主全量那条线）：

```
04_产出/博主/<昵称>_<账号ID>/
    _索引.xlsx              统一字段 30 列，含「逐字稿」「抓取时间」
    _逐字稿合集.md           灵造那份完整字幕合集（得到大脑没有这个）
    <发布日期>_<标题>/
        逐字稿.md            信息头 + 正文 + 逐字稿（一个文件看全貌）
        封面.webp / .jpg      有才放
04_产出/图片/<昵称>_<账号ID>/<笔记ID>.webp    封面池
04_产出/表格/                                  成品表
```

**命名规矩**（改之前想清楚）：
- 博主目录 = `昵称_账号ID` —— 改昵称了也能对回账号
- 单条目录 = `发布日期_标题`，**不用 `001` 序号** —— 增量抓时序号会错位
- 单条目录里的文件名**固定**（`逐字稿.md` / `封面.\*`），哪个博主都一样；
  固定了才能用一个脚本跑全部博主
- 身份永远认**笔记 ID**，文件夹名只是给人看的

## 下载类动作：封面 / 视频（2026-09-20 起）

**三条规则（用户拍板，别改）：下载归加工层；按源分开；封面和视频各自成文件，不合在一起。**
用户原话：「因为每一个就是他们的脚本规则是不一样的，有的抓的是临时链接，有的是抓的是永久链接。」

| 文件 | 干什么 | 要凭证吗 |
|---|---|---|
| `03_加工/01_lingzao/cover.py` | 灵造补封面。读本地 profile JSON（也吃成品表 xlsx）→ 下到图池 | **不要**（URL 就在 JSON 里） |
| `03_加工/02_getnote/cover.py` | 得到大脑补封面。读本地 `blogger-covers` 快照 → 下到图池 | **不要**（URL 就在快照里） |
| `03_加工/<源>/video.py` | 视频**占位接口**，不下载 | — |

**两个源的封面规则完全不同 —— 这正是要分开写的原因：**

| | 灵造 | 得到大脑 |
|---|---|---|
| 签名 | **带**（`t=` 时间戳） | **不带** |
| 有效期 | **约 3 小时** | **永久** |
| 语义 | **抢救**（晚了就废） | **补缺**（随时都行） |
| 字段 | `media.cover_large_url` | `post_cover` |

⚠️ **别把一边的紧张感套到另一边。**

**要 key 的那步留在采集层**：得到大脑走 HTTP 要开放平台凭证，那是
`01_采集/02_getnote/collect.py` 的事。加工层只做「本地数据 → 下载文件」，不碰配置。

★ **得到大脑的封面不用单独补**（2026-09-20 实测更正）：详情接口
`/blogger/content/detail` 的返回里就带 `post_cover`，采集 `details` 时**随 JSON 一起落盘**，
表里第 29 列「封面URL」直接有值。

封面**图**由 `bundle.py` 归位，两步：**先取图池，图池没有就用手上那个 URL 现下**
（得到大脑链接不带签名、不过期，现下是安全的）。**所以封面不会缺。**

- 采集层原来那个 `cover` 动作（专门拉一次列表只为拿封面）**已删** —— 详情里就有，白跑一趟。
- 加工层的 `03_加工/02_getnote/run.py cover` **保留**，用途变成「把图池一次性补满」（缓存）。
  实测：把图池目录挪走再跑 `blogger`，输出 `封面 有 20（图池 0 ｜ 现下 20）｜ 缺 0` —— 兜底真的生效。

**视频为什么是空的**：
- 灵造只给**时长**、不给地址 —— 而且**两种命令字段名不一样**（踩过，静默算错）：
  `analyze-user-profile` → `media.video_duration_seconds`（秒）；
  `search-notes` → `media.video.durationMs`（毫秒）
- 得到大脑的 `post_url` 是抖音**分享页**（`iesdouyin.com/share/video/…`），不是 `.mp4` 直链

要真下得再加一层解析（yt-dlp 之类）= 新增依赖。所以先摆「接口 + 询问流程」：
**抓取完成后先问用户 —— 这次有几条视频、要不要下、下要多少钱、占多大；
默认「下」，也能改成默认不下，但不管默认是什么都先问一次**（要报成本，不能闷头下）。

## 得到大脑（getnote）的外抓链路

**⚠️ 大前提：本项目只用「外抓」命令，不碰用户私人笔记**（2026-09-19 用户划的边界）。

### 能用（外抓口子）

★ **2026-09-20 起一律走开放平台 HTTP API，不用 CLI**（用户定的）。

```bash
python 01_采集/02_getnote/collect.py bloggers --topic <topic_id>             # 博主列表 → follow_id
python 01_采集/02_getnote/collect.py contents --topic <topic_id> --follow X   # 内容列表 → alias 清单
python 01_采集/02_getnote/collect.py details  --topic <topic_id> --follow X   # ★ 详情 → 跑完自动出表
```

`details` 内部先拉一次列表拿 id、再逐条拉详情；**跑完自动调加工**（见「抓完必须接加工」那节）。
`--no-clean` 可关它；`--limit` 默认 20；`--gap` 默认 3.5 秒（被限流就调大）。

（订阅新博主 `kb blogger-follow`、直播 `kb lives` 暂时只有 CLI，用到再说。）

### 禁用（碰私人笔记，一条都不许调）

`notes` / `note` / `note original` / `note transcript` / `note attachments` /
`note timeline` / `note quick-note` / `note todos` / `search` / `tag *` /
`kb`（知识库笔记列表）/ `save` / `note update` / `note delete` / `note share`

⚠️ 这是**约定隔离**，不是权限隔离 —— CLI 用的是用户账号的完整授权，
脚本不调 ≠ 权限上读不到。唯一例外：**用户当轮明确点名**要看自己某条笔记时可以调，
但那不是常规动作，也不许写进 `ACTIONS`。

### 三条 HTTP 接口（前缀 `/open/api/v1/resource/knowledge`）

```
GET /bloggers?topic_id=                                博主列表
GET /blogger/contents?topic_id=&follow_id=&page=       内容列表
GET /blogger/content/detail?topic_id=&post_id=         内容详情 ★ 逐字稿 + 封面
    头：Authorization: <api_key>（⚠️ 不带 Bearer） + X-Client-ID: <client_id>
```

**博主列表**比 CLI 多两个字段：`account_avatar`（头像）、`follow_link`（抖音主页）。

**内容详情返回 12 个字段**（官方文档只写 6 个）：
`post_id_alias / post_name / post_type / post_cover / post_subtitle / post_url /
post_title / post_summary / post_media_text / post_create_time / post_update_time /
post_publish_time`

→ **`post_cover` 在详情里就有**，所以不用再单独拉列表补封面（旧的「两步法」已废）。

**翻页**：固定 20 条/页（`page_size` 传了没用），靠 `has_more` 判断。**桶级限流**，
连调两个接口就撞 429、等 4 秒恢复 → 每条之间停 3.5 秒起。20 条约 2 分钟，665 条约 40 分钟。

### 落盘命名（改名字之前，先去加工层确认它靠什么认文件）

```
02_储存/02_getnote/blogger/
    _bloggers_<昵称>_<follow_id>.json          博主列表
    _blogger-contents_<昵称>_p1.json           内容列表
    _blogger-content_<post_id_alias>.json      单条详情
```

⚠️ **两条硬要求**（2026-09-20 都踩过，详见纠错 ⑭⑮）：

1. **不能带日期前缀** —— 跨天并存，同一条内容变两个文件，加工层读双份
2. **必须保住前导 `_`** —— 加工层靠 `*_blogger-content_*` 这种 **glob** 认文件

### 指定链接 → 结构化笔记（这条是全自动的）

```bash
"$EXE" save "<链接>" --title "<原帖标题>" --idempotency-key <key> -o json
```

- **同步的**：约 40 秒直接返回完整笔记，**没有 task_id、不用轮询**。
  官方文档说普通链接是异步（要轮询 `task/progress`）—— 那是 **HTTP API** 的行为，
  **CLI 把异步包装成了同步**。别白写一套轮询逻辑。
- **一次调用全给你**：`data.note` 里同时含 `content`（AI 解读版）和
  `web_page.content`（原文版），**不需要再调 `note` 取一次**。
- `--idempotency-key` 防重复保存；`--topic-id` 指定落进哪个知识库。
- 实测 `source: openapi`（手动在 App 里存的是 `app`）—— **能区分两种来源**。
- 它接受**任意网页链接**，不限小红书。这才是它比灵造值钱的地方。

## 纠错清单 ★ 以下全是实测踩过的，按现象查

### ① 参数里的 `&` 让 CLI 报「不是内部或外部命令」

**现象**：`'xsec_source' 不是内部或外部命令`，rc=1，没落盘。
**原因**：`lingzao.cmd` 是批处理，Python 传参数组时只在含空格/Tab 才加引号，
URL 里的 `&` 被 cmd.exe 当成命令分隔符切开。
**修法**：`01_采集/01_lingzao/collect.py` 的 `run_cli()` 已处理 ——
参数含 `[&|<>^()\s]` 时自己拼命令行 + 补引号，走 `shell=True`。
**注意**：`02_getnote/collect.py` 里是同一段代码的副本，**那份还没修**（用户要求别全改）。

### ② 灵造的封面 URL 会过期，而且只有约 3 小时

**现象**：`HTTP 498`（也会看到 403）。
**原因**：URL 查询串里的 `t=` 是**抓取那一刻**的十六进制时间戳，签名有寿命。
**实测**：16:11 抓的，19:23 去下 → 全废；8-04 的 → 全废。
**2026-09-20 又测一次**：40 条老数据 → 24 条 498 + 16 条 403，**一张都没救回来**。

**修法（两条腿，都要有）：**
1. **采集层** `download_covers()` 落盘后立刻抢一遍 —— 这是主路，别绕过
2. **加工层** `python 03_加工/01_lingzao/run.py cover "<路径>"` —— 抓完发现漏了、失败了，
   趁窗口没过赶紧补一次。能吃 profile JSON，也能吃只剩一张 xlsx 的老成品表

⚠️ **窗口一过就真没了**：JSON 里存的是**已经签好名**的 URL，过期就是废纸。
想拿新 URL 只能**重新调灵造抓一次（花 credits）** —— 必须先跟用户报账。

**关键**：封面池的文件名用**笔记 ID**（永不变），取的时候按「目录名后缀 = 账号ID」匹配。

### ③ 但 artifact 链接不过期 —— 老数据能靠它复活

**现象**：只有一张几个月前导出的成品表，没有原始 JSON，看着像废了。
**关键**：表里若留着**「字幕全文索引」**列，那个 `assets-tian.midao.site` 的 URL
**不带签名、长期有效**。实测 8-28 生成的链接，9-19 还能下。
**做法**：下下来当逐字稿合集用，配合 `03_加工/01_lingzao/table.py` 还原整个博主目录。
（**新数据不用管这步** —— 采集时已经自动下了，见 ⑤。）

### ④ 逐字稿缺失分三种，只有一种能靠重抓救

先看那两个硬指标：**字幕状态** 和 **时长**。

| 情况 | 特征 | 原因 | 重抓有用？ |
|---|---|---|---|
| `failed` | 有时长、媒体信息齐全 | 灵造转写任务失败 | ✅ **实测 18 条修好 17 条** |
| `missing` + 有时长 | 时长 11s/18s 这种 | 视频本身没人声 | ❌ 白花钱 |
| `missing` + 时长为 `None` | **媒体信息整个拿不到** | 平台对老视频不给源信息 | ❓ 未知 |

**别把「没抓到」和「源头没有」混为一谈。** 重抓前先按这张表分个类。

### ⑤ 「字幕状态 = ready」也不保证有全文

**现象**：表里写着 ready，但 `plain_text` 是短的。
**原因**：JSON 里的字幕是**截断版**（`truncated: true`），全文只在合集 artifact 里。
**实测**：某条 JSON 里 1203 字，合集里 2007 字。16 条有字幕的里 14 条正好撞 1203 这个顶 ——
**长度一堆一样 = 还在用截断版**。
**修法**：优先用 `_完整字幕合集.md`，按 `笔记 ID:` 匹配取全文。

**⚠️ 找全文的位置**：`data.artifacts.subtitle_markdown`（**响应顶层**），
**不在** `items[].artifacts` 里 —— 后者是空的，第一次就查错了地方、
差点判成「没有全文」。字段（文档没写全，实测）：

```
status / url / format / size_bytes / sha256 / r2_key / expires_at / visibility
```

★ **`sha256` 是白送的完整性校验**：下载后本地算一次比对。
只比 `size_bytes` 不够 —— **内容坏掉不一定改大小**。实测 4 份全部一致。

**2026-09-20 起这步已经自动化**：`01_采集/01_lingzao/collect.py` 落盘后顺手下，
**落两个文件**（同目录、同前缀）：

- `<源 JSON 名字>_完整字幕合集.md` —— 正文，原样落盘（加工层按同前缀精确配对）
- `<源 JSON 名字>_artifacts.json` —— **来源记录**：URL / status / size / sha256 / 下载结果
  （`write_artifact_sidecar()`；没下成的也写，记下原因，不静默略过）

下载不调灵造 API、不扣积分（公开签名静态文件，`expires_at: null`）。
用户 2026-09-20 的要求：「**原始数据层也要把逐字稿的 URL 跟着抓下来**」——
原始 JSON 里虽有 `data.artifacts`，但它是**整批一份**、埋在几百 KB 深处，
而且「下载成没成 / 校验过没有 / 落地叫什么名」这些**结果根本不在响应里**，所以单独记。

### ⑥ 逐字稿必须按**笔记 ID** 匹配，绝不能按标题

**原因**：**同一个博主会有同名笔记**。实测 nana 的账号里有两条都叫
「Codex 一键智能剪辑 Skill 开源了！」（08-08 和 08-12）。按标题匹配必然串行。
**修法**：合集里每条都有 `- 笔记 ID:`，用它对齐。核心实现见 `bundle.py` 的 `parse_collection()`。

### ⑦ 读成品 xlsx 时，表头不在第 1 行

**版式**：第 1 行是合并标题、**第 2 行是空的**、**第 3 行才是表头**、第 4 行起是数据。
**修法**：别写死行号 —— 扫前 15 行，找含「标题」或「笔记ID」的那行当表头。
见 `03_加工/01_lingzao/table.py` 的 `load_rows()`。
另外**按列名取值，不按列序号**（老表 24 列、新表 30 列），列名要归一化全角半角。

### ⑧ 重跑必须是幂等的

**做法**：`bundle` 重跑前先扫博主目录，读每个单条目录里 `逐字稿.md` 的 `- 笔记 ID：` 行
认领已有文件夹，所以同一批数据重复导出**不会变成 `xxx_2`**。
（2026-09-19 起 `笔记信息.md` 已废、合并进 `逐字稿.md`，认领逻辑同时兼容新旧两种格式。）
不要改成「一律新建目录」。

### ⑨ ★ 标题必须自己传 —— AI 会偷偷改掉（用户定的铁律）

**现象**：存进去的标题和原帖不一样。
**实测**：原帖「14 【恐惧很深的人，乐在其中，会很有厚度 - 谢胜子认知修炼】」
→ 存进去变成 AI 生成的「深度认知：恐惧深厚个体的人生成长路径解析」。

**★ 原标题去哪找：`attachments[0].title`（三条全验证过）**

| `data.note.title`（AI 版，会被改） | `attachments[0].title`（原帖标题） |
|---|---|
| 深度认知：恐惧深厚个体… | 恐惧很深的人，乐在其中，会很有厚度 |
| 零成本变美方案：7条… | 以前我朋友总觉得变美很难，… |
| 国学视域下本真气韵修养… | 修出人的"大有"气象 |

- ⛔ **别按长短判断它是不是标题** —— 小红书的标题**常常就是正文第一句**，
  按「长的就是正文」判会直接误判（踩过）。
- 可能被服务端**截断**，长标题会切尾。
- `source` 无论是 `app` / `openapi` / `web`，这个字段都有值。

**⚠️ 分享文本解析的坑**：`【<标题> - <作者> | 小红书…】` 里的 **` - <作者>` 不是标题**。
实测 ` - 谢胜子认知修炼` 是博主名，服务端抓的原帖标题只有前半段。
→ **最佳做法：`save` 完回读一次，用 `attachments[0].title` 校正 `data.note.title`。**
（服务端才是权威；分享文本会被作者名污染。）
**修法**：`save` **必须带 `--title`**。原帖标题从**小红书分享文本**里解析，真实形态：

```
14 【恐惧很深的人，乐在其中，会很有厚度 - 谢胜子认知修炼 | 小红书 - 你的生活兴趣社区】 😆 1ehK7BMVh3DMQek 😆 https://…
```

→ 取 `【】` 之间、去掉 ` | 小红书…` 后缀，就是原帖标题。
**用户粘进来的常常是整段分享文本而不是裸链接** —— 采集动作要能同时抠出标题和 URL。
已经存错了要改回来：`getnote note update <id> --title "<原帖标题>"`
（**改 title 不需要 `--yes`**，只有改 `--content` / `--tag` 才要；改完必须重读验证）。

### ⑩ 得到大脑会 429 限流，采集必须节流

**现象**：`429 / code 10202 / reason=qps_bucket_exceeded / retryable: true`。
**实测**：连着调两个接口就撞上，**等 4 秒就恢复**。
**做法**：每条之间停 **3.5 秒**起。实测 20 条 detail 耗时 105 秒 → 665 条约 58 分钟。
额度（read）日 20000 / 月 200000，够用；撞的一定是 QPS 桶，不是配额。

### ⑪ ★ 得到大脑一律走 HTTP API，别再用 CLI（2026-09-20 用户定）

**理由**：HTTP 的详情接口给 **12 个字段**，**带 `post_cover`（封面）**；
CLI 的详情只有 10 个、**没有封面**。走一条通道，就少一处「两边不一致」。

```
HTTP 详情：post_id_alias post_name post_type post_cover post_subtitle post_url
           post_title post_summary post_media_text post_create_time
           post_update_time post_publish_time
CLI 详情： 10 个，少了 post_cover / post_update_time（其余同名同义）
```

⚠️ **官方文档写少了**：详情接口文档只列 6 个字段，实测 12 个。
**别拿文档的字段表当白名单校验**，会漏数据。

**两个坑两条通道都有：**

- 详情里 `post_id_alias` / `post_title` / `post_subtitle` **都是空串** →
  身份只能从**落盘文件名**取；标题用 `post_name`
- `save` 在 CLI 里是**同步**的（40 秒返回），HTTP 是异步要轮询 ——
  将来把 `save` 接进采集层时注意

### ⑫ `post_url` 是 483 字的超长链接，落表前必须洗

抖音分享链接带 `share_sign` / `ts` / `u_code` / `did` 一堆参数，**还可能过期**。
落表前只留 `https://www.iesdouyin.com/share/video/<video_id>/`。

### ⑬ 链接笔记有两个正文，是两个不同的字段

- `web_page.content`（= `note original` 的 `original`）= **网页原文**
- `content` = **得到大脑 AI 二次加工的结构化笔记**（带表格和洞察，`entry_type=ai`）

**一份内容两条正文，入库前要想清用哪条**，别默认只取一个。

### ⑭ 落盘文件名带日期 → 加工层读到双份

**现象**：抓了 20 条，加工层报「条数 40」。
**原因**：详情落盘名写成 `<日期>_blogger-content_<alias>.json`，今天跑生成新的一批，
和昨天那批**并存** —— 同一个 alias 变成两个文件。
**修法**：**去掉日期前缀**。哪次抓的看文件 mtime（`collected_at` 就是从那儿取的）。

### ⑮ 文件名丢了前导 `_` → 加工层完全认不出

**现象**：`归档失败：… 里没有 *_blogger-content_*.json` —— 明明文件就在那儿。
**原因**：加工层靠 **glob** 认文件（`bundle.py` 的 `*_blogger-content_*`、
`_author_from_dir` 的 `*_bloggers_*`）**+** **正则**（`adapter.py` 的 `_RE_*`）。
少了前导 `_`，两处都对不上 → `detect_command` 认不出 → 文件全被跳过。
**修法**：文件名保住前导 `_`：`_blogger-content_<alias>.json`。

**★ 通用教训：改落盘命名之前，先去加工层确认它靠什么认文件。**
这个项目里认文件名的地方有**两处**（glob + 正则），改名要同时过这两关。

### ⑯ 派生物必须用**实际落盘名**配对，不能用你「打算」写的名字

**现象**：字幕合集下载了，但加工时死活配不上，逐字稿退回截断版。
**原因**：`save_raw()` 遇重名会加 `_2`（同一天重抓同一博主就会 —— nana 就有一份
`…67d22c9_2.json`）。如果你用**原始 filename** 去命名派生物，
它会变成 `…67d22c9_完整字幕合集.md`，而 JSON 实际叫 `…67d22c9_2.json` → 配不上。
**修法**：`save_raw` 返回路径后，用 **`path.stem`** 去命名派生物。

**★ 通用教训：凡是「跟着主文件走的派生物」（合集、缩略图、附属数据），
命名一律以主文件**实际落盘后的名字**为准。**

### ⑰ 测「某个缓存不可用」时，改名/移动要真的破坏匹配条件

**踩过的**：想验证「图池不可用时 bundle 会不会现下兜底」，
把图池目录 `谢胜子_1397022` 改名成 `__Bak_谢胜子_1397022` ——
**它仍然以 `_1397022` 结尾**，而 `find_pool_cover()` 正是按「目录名后缀 = 账号ID」
匹配的，所以照样命中，测出来的「图池 20 ｜ 现下 0」是假象。
正确做法：改成 `Bak_谢胜子_tmp`（不以账号 ID 结尾），才真的测到兜底。

**★ 通用教训：做「屏蔽某个东西」的测试时，先确认你的屏蔽手段真的能让它不被找到。**
外加：这类测试一定用 `try/finally` 恢复现场。
